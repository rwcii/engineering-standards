# WDR 009.1: Track Raw Development Usage

**Date:** 2026-11-25
**Status:** Accepted
**Authors:** Robert Capps

---

## Executive Summary

Extend [WDR 009](009-ai-provenance-and-accountability.md) with raw model usage tied to
the commits it helped produce or review. Keep the evidence out of commit text. Preserve
what the collector measured and make gaps visible when publishing or merging a change.

## 1. Problem Context

### The Problem

A development session may contribute to several commits, and a review can use tokens
without changing a file. The same response can appear in several captures. Per-commit
records can then double count it, or lose it when a branch is squashed. A report with
missing usage can also look complete if it substitutes zero.

### Requirements

1. Keep the evidence tied to its commit and distinguish development from review.
2. Preserve measured values, missing data and event identity through sync and merge.
3. Use the out-of-band provenance channel defined by WDR 009, Decision 3.

### Scope

Raw usage for the commits and reviews covered by a project's adoption. WDR 009 governs
authorship, accountability and the audit trail.

## 2. Decision 1: Preserve Raw Usage Across Development and Merge

### Decision

Capture available usage after each commit in machine-readable provenance alongside
the commit. Use an out-of-band record so the commit message, trailers and authorship
remain separate from the measurement. Keep the model identifier and version, harness
version, capture time, a safe-to-publish run reference, and the activity that produced
the usage, such as writing or review. Bind review activity to the full reviewed head.

Store raw input, output, cache-write and cache-read token counts as separate fields.
Preserve the provider's definitions, including when one category is a subset of another.
Capture is best effort. Omit unavailable measurements and state why if their absence
leaves the capture incomplete. When a capture is missing entirely, record unknown usage
with a reason. A report with unknown or incomplete usage says it is **INCOMPLETE**.
Only a verified system action that used no model gets an empty usage record.

Count each provider response once using a stable event identity. Repeated identical
events leave the record unchanged. Conflicting values under the same identity are
reported and rejected before changing the stored record. Synchronization joins the
independent event sets. Fetch into separate storage before reconciliation so it cannot
overwrite the canonical records.

Put capture and recount in the publication checklist. Recount and synchronize the
branch head after its last commit and review and before each push. Recount after a later
review of the same head and after a replacement head is reviewed. Include bound review
sessions even when they made no commit. Before a merge, verify the recount still covers
the head and reviews that are being merged.

At a squash, aggregate the branch's usage onto the actual result and verify it there.
Count each event once across the inputs. A missing input record raises an alarm and
leaves the report incomplete. A project may use a post-merge guard with a repair path
that restores the missing record or records why the usage is unknown, then verifies
the aggregation again.

- **Context:** What should the workflow retain about model use across commits, reviews and
  squash merges? The options were a branch-level estimate, raw usage tied to commits and
  review heads, or usage records paired with monetary estimates.
- **Reason and scope:** Raw event evidence can be reconciled and audited across history
  changes. This decision covers usage measurements for the work included in a project's
  adoption. The project records when that coverage begins.

### Alternatives Considered

| Alternative | Description | Reason declined |
| ----------- | ----------- | --------------- |
| Branch-level estimate | Enter one total for the branch at publication | Loses per-commit and review evidence and can conceal missing records |
| Cost tracking | Add a price table, monetary figures or cost derivation | The approved scope is raw usage. Price assumptions change independently of what the collector measured |

### Enforcement

An adopting project supplies the capture, unknown-usage, recount, synchronization and
aggregation tools. For example, a project using Git notes keeps the fetch destination
separate from the canonical notes ref and reconciles the captured events before updating
that ref. `koinon-provenance` can coordinate the steps through the adopter's
`.koinon/skills/provenance.md` facts. The project keeps native identifiers private when
they cannot be published and exposes a safe reference in shared outputs.

## 3. Conclusion

Per-commit raw records preserve measured usage through reviews and squashes. Stable event
identities keep recounts repeatable, and explicit unknowns let a reader distinguish
missing evidence from measured usage.
